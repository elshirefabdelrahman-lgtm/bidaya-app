# نشر Bidaya على Vercel

نفس مستودع GitHub `elshirefabdelrahman-lgtm/bidaya-app` يخدم Web وAndroid. الموقع يقرأ ويكتب في مشروع Supabase الحالي؛ لا توجد قاعدة بيانات منفصلة للموقع أو بيانات Demo تلقائية.

## Import أول مرة

1. في Vercel اختار Add New → Project، ثم Import للمستودع `bidaya-app` من حساب GitHub الصحيح.
2. الفرع Production هو `main`، وRoot Directory جذر المستودع `./`.
3. Framework Preset: Other. إعدادات vercel.json تضبط Install Command إلى `npm ci` وBuild Command إلى `npm run build` وOutput Directory إلى `dist`.
4. Node.js: 24.x، وهو محدد في package.json. لا تختار npm start كأمر بناء؛ ده خادم التطوير المحلي فقط.
5. لا توجد Environment Variables إضافية مطلوبة لبناء الواجهة الحالي. src/config.js يحتوي عنوان Supabase وPublishable Key عامين فقط. لا تضف Service Role Key أو أسرار Edge Functions إلى الواجهة أو إعدادات البناء.
6. اضغط Deploy، وانتظر نجاح البناء، ثم انسخ رابط Production الثابت للمشروع، وليس رابط Preview مؤقتًا.

## خطوة مطلوبة بعد استخراج الرابط

الصفحة يمكن نشرها قبل إضافة النطاق إلى Supabase، لكن تسجيل الدخول من النطاق الجديد يحتاج ضبطه أولًا:

- أضف Origin الإنتاج الدقيق (بلا slash أخير) إلى ALLOWED_ORIGINS في Supabase مع إبقاء `http://localhost:4174` و`https://localhost` حتى يظل المحلي وAndroid مسموحين. لا تستخدم wildcard عامًا.
- اضبط APP_URL على رابط الإنتاج المناسب لاستعادة كلمة المرور.
- اضبط Supabase Auth Site URL وRedirect URLs للرابط الفعلي، مع الحفاظ على روابط الاختبار المطلوبة.
- اختبر Login وapp_snapshot وapp_command وإدارة الحسابات حسب الصلاحية، واختبر حفظ بيانات مأذون بها ثم تحديث جهاز ثانٍ. لا تعتبر نجاح البناء المحلي إثباتًا لعمل CORS على رابط لم يُنشأ بعد.

لا تُعد تشغيل migrations ولا تغيّر بيانات قاعدة البيانات لاستضافة الواجهة. مستخدمو Web وAPK يرون البيانات المركزية نفسها وفق صلاحياتهم بعد التحديث والتنقل؛ لا يوجد بث Realtime لكل حركة.

## التحديثات

Push إلى main يُنتج نشر Web جديدًا بعد ربط المستودع بـVercel. تحديث Android يتم بمسار OtaKit القائم بصورة مستقلة. تغيير النطاق الدائم لاحقًا يحتاج مراجعة إعدادات CORS وAuth مرة أخرى.

ملفات Vercel: vercel.json لإعداد البناء والترويسات، و.vercelignore لاستبعاد الملفات المحلية غير المطلوبة عند استخدام CLI. النشر يقتصر على dist؛ لا توجد rewrite عامة تجعل مسارات الملفات الخاصة تعيد صفحة الدخول.

## التحقق المنفذ محليًا

`npm run test:web-build` يبني dist ويخدمه على منفذ محلي منفصل، ثم يفحص تحميل الواجهة والصور وتسجيل حالة ودفعة بخادم محاكاة وتصدير XLSX من الحزم المجمعة والعرض على الهاتف. يفحص أيضًا أن مسارات الكود وSQL والنسخ الاحتياطية و.env تُرجع 404. جميع طلبات Supabase أثناء هذا الاختبار معترضة، ولا تُقرأ أو تُكتب بيانات المركز الحقيقية. لم ينشئ هذا الإعداد مشروع Vercel أو ينفذ Deploy.

## حالة الإنتاج

رابط الإنتاج: https://bidaya-app-three.vercel.app . ثبت أن طلبات OPTIONS للوظيفتين كانت مرفوضة بـ400 من هذا النطاق؛ أضيف النطاق الدقيق إلى ALLOWED_ORIGINS مع إبقاء المحلي وAndroid. ضُبط APP_URL وAuth Site URL وRedirect URLs للموقع مع الحفاظ على روابط Redirect السابقة. بعد الإصلاح نجحت OPTIONS من النطاقات الثلاثة المسموحة للوظيفتين (6 طلبات)، وظل نطاق غير موثوق مرفوضًا للوظيفتين (طلبان). أكد المستخدم نجاح الدخول الحقيقي من الموقع. لم يُطلب أو يُستخدم Password أو Token المستخدم أثناء التشخيص.
