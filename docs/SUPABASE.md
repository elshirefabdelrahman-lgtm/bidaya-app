# دليل الربط التالي مع Supabase — لم يُنفّذ بعد

## ما ترسله للمساعدة في الربط

أنشئ مشروع Supabase من حسابك. أرسل Project URL وPublishable/Anon Key العام فقط. لا ترسل كلمة مرور قاعدة البيانات أو Service Role/Secret Key. لم نضع قيمًا افتراضية أو ننشئ مشروعًا تلقائيًا.

## خطوات الربط بعد إنشاء المشروع

1. راجع الملفات الخمسة في migrations ثم طبّقها بالترتيب على مشروع جديد عبر SQL Editor أو Supabase CLI. الملفات تأسيسية وليست معدة لإعادة التطبيق فوق جداول قائمة. احتفظ بنسخة احتياطية إن كان المشروع به بيانات.
2. أنشئ حساب أول مدير من لوحة Supabase Auth ببريد تملكه وكلمة مرور قوية. عطل التسجيل العام من Auth Settings؛ إنشاء الموظفين يكون عبر الوظيفة الإدارية.
3. أضف profile الأول من SQL Editor موثوق، باستخدام UUID المستخدم الذي أنشأته في Auth. لا توجد كلمة مرور أو مفتاح سري في SQL التالي:

```sql
-- استبدل UUID والبيانات الفعلية أولًا، ولا تنفذها كما هي.
insert into public.profiles(id,name,username,email,role,active,permissions,branches)
values ('UUID-OF-YOUR-AUTH-USER'::uuid,'مدير المركز','center_admin','YOUR-EMAIL','Super Admin',true,'{}','{}');
```

4. انشر `login` و`admin-users`. config.toml يعطل فحص JWT التلقائي لهما؛ وظيفة login عامة مع تحديد محاولات، وadmin-users تتحقق بنفسها من JWT باستخدام getUser ومن Super Admin بقاعدة البيانات. لا يجوز إزالة هذا التحقق.

```powershell
supabase link --project-ref YOUR_PROJECT_REF
supabase functions deploy login
supabase functions deploy admin-users
```

5. من Edge Function Secrets، اضبط `ALLOWED_ORIGINS` كقائمة مفصولة بفواصل للنطاقات الفعلية، و`APP_URL` كعنوان التطبيق الكامل لاستعادة كلمة المرور، و`RATE_LIMIT_SALT` كقيمة عشوائية قوية. مفاتيح SUPABASE_URL وSUPABASE_ANON_KEY وSUPABASE_SERVICE_ROLE_KEY توفرها بيئة Supabase فقط؛ لا تنسخ الأخير إلى المشروع أو المتصفح. استخدم لوحة Secrets لتجنب كشف القيم في سجل أوامر shell.
6. اضبط Auth Site URL وRedirect URLs على العنوان نفسه، وأعد SMTP وقالب رسائل الاستعادة. رابط الاستعادة الحالي implicit hash؛ يتم حذف التوكن من URL بعد قراءته ويحفظ في الذاكرة فقط. اختبر عمر التوكن والرابط مرة واحدة والبريد الفعلي. تفعيل PKCE لاحقًا يستلزم إضافة تبادل code بدل افتراض دعم الواجهة له الآن.
7. ضع URL والمفتاح العام فقط في `src/config.js`. لا تستخدم service role أو secret key هنا. الاستدعاءات من الواجهة تستخدم Publishable/Anon + access token، والكتابات المالية عبر RPC.
8. سجّل دخول المدير وأضف الفروع الحقيقية. ثم أنشئ حسابات الأدوار بصلاحيات وفروع صريحة. إنشاء الحساب يحفظ كلمة المرور داخل Supabase Auth فقط؛ لا يخزنها في profiles أو audit.
9. راجع Security Advisor والجداول والـ grants وRLS في المشروع الفعلي. اختبر direct REST وRPC بحسابات منفصلة؛ لا يكفي نجاح الأزرار أو إخفاؤها.

## عقد الواجهة والخادم

- `POST functions/v1/login` ← `{identity,password}`، يعيد session Auth؛ `{identity,recover:true}` لطلب الاستعادة.
- `POST rest/v1/rpc/app_snapshot` ← `{}`، يعيد arrays اللازمة للواجهة وcurrentUser بعد RLS.
- `POST rest/v1/rpc/app_command` ← `{kind,input,request_id}`، ينفذ عملية ذرية؛ التفويض حسب المستخدم الموثق، ولا يقبل actor من المتصفح.
- `POST functions/v1/admin-users` ← `{kind,input}`؛ يدعم user/userEdit/resetPassword، لمدير النظام فقط. قائمة permissions والفروع محدودة ومراجعة بالخادم.
- `PUT auth/v1/user` لتعيين كلمة مرور جديدة باستخدام recovery access token؛ تسجيل الخروج بعدها.

إنشاء profile بعد Auth لا يمكن أن يكون داخل المعاملة نفسها. وظيفة الإنشاء تنظف حساب Auth اليتيم إن فشل إنشاء profile؛ إن حدث عطل شبكة أثناء التعويض يلزم مراجعة لوحة Auth. تعديل حساب موجود يسحب وصول قاعدة البيانات أولًا، ثم يغير Auth ويعيد تفعيل profile عند النجاح. سجلات المراحل محفوظة في audit. اختبر حالات الفشل هذه قبل التشغيل الحقيقي.

## بوابة قبول الربط الحقيقي

- دخول بالبريد واسم المستخدم، كلمة خاطئة، مستخدم معطل، توكن منتهي، تحديث جلسة، خروج وإعادة دخول.
- إنشاء حساب وتغيير دوره وصلاحياته وفروعه، تعطيله وإعادة تفعيله، وإعادة تعيين بالبريد؛ لا يستطيع المستخدم رفع صلاحياته أو تعديل profiles مباشرة.
- تنفيذ الحالة 001 بتعاقد 30000 ودفعات 10000 و5000 و3000؛ المتبقي 12000 من جهاز ثانٍ بعد التحديث/إعادة الدخول.
- دفعتان متزامنتان قرب الرصيد المتبقي؛ لا يقبل الخادم تجاوز التعاقد. إعادة إرسال request_id نفسه لا تسجل حركة ثانية، وتغيير محتواه بنفس المفتاح مرفوض.
- راتب 6000، سلفتان 1000 و500، تسوية 1500، صافي راتب 4500، والخزينة لا تخصم 1500 مرة ثانية.
- RLS لكل دور وكل فرع، حتى عند استدعاء REST/RPC خارج الواجهة، وتأكد أن بيانات الفرع الآخر لا تصل في response.
- تعطيل الحساب أثناء جلسة مفتوحة يمنع قراءة وكتابة جديدة؛ تحديث القائمة يكشف الحالة. البيانات التي وصلت سابقًا إلى جهاز مستخدم مصرح له لا يمكن سحبها عن بُعد.
- Audit قبل/بعد، رفض UPDATE/DELETE عليه، وبقاء الحركة الملغاة في التاريخ دون إدخالها في المجاميع.
- Export XLSX وPDF بالعربية عبر بيانات حقيقية محدودة، واختبار النسخ الاحتياطي واسترجاعه.

SQL المحلي اجتاز اختبار PGlite، وملفات Edge اجتازت type check. لا تدّعِ أن أي بند متعلق بالسحابة أو البريد أو جهازين اجتاز الاختبار قبل تنفيذه فعليًا.
