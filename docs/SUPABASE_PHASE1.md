# المرحلة الأولى لربط Supabase — 1 نوفمبر 2026

## ما نُفذ

- `src/config.js`: ضبط Project URL والمفتاح Publishable العام المقدمين من المستخدم. لا Service Role Key أو Secret Key في الواجهة.
- `src/repository.js`: المفتاح العام في apikey فقط؛ Access Token للمستخدم في Authorization عند وجود جلسة. دخول/استعادة عبر login، إدارة الحسابات عبر admin-users، قراءة عبر app_snapshot، وحفظ عبر app_command بمعاملاته kind/input/request_id. أضيف التحقق من إعداد الاتصال ورفض المفاتيح الإدارية، ورسائل خطأ للشبكة والبيانات غير المكتملة دون أي fallback إلى Demo.
- الجلسة في الذاكرة فقط، وتجديد واحد مشترك بين الطلبات المتزامنة، وتدوير Refresh Token، وإلغاء الحالة المحلية عند انتهاء الجلسة أو تعطيل المستخدم. الاستجابات المتأخرة لا تعيد جلسة بعد الخروج. انقطاع شبكة عابر أثناء التجديد يبقي الجلسة قابلة لإعادة المحاولة؛ رفض توكن التجديد يمحوها.
- `src/app.js`: ربط انتهاء الجلسة بمسح بيانات الواجهة والعودة إلى تسجيل الدخول، مع الحفاظ على Demo كخيار منفصل صريح. تحديث نص إرشادي فقط؛ دون تغيير CSS أو الصور أو الألوان.
- `src/screens.js`: إضافة الهاتف إلى نموذج تعديل الحالة وملئه بالقيمة السابقة. المستودع يعيد إرسال القيمة الحالية إذا غاب phone أو كان null. إرسال قيمة بديلة صراحة يحدّثها؛ إرسال حقل فارغ صراحة يعني إفراغه.
- `package.json`: تشغيل الاختبارات المحلية تسلسليًا وبترجمة WebAssembly الأساسية فقط (liftoff-only) لتقليل استهلاك الذاكرة، وإضافة أمر test:supabase-ui.
- الاختبارات: توسيع tests/repository.test.js، وإضافة tests/repository-sql.test.js وtests/e2e/supabase-flow.mjs، واعتراض الطلبات الخارجية في اختبارات المتصفح القديمة حتى لا ترسل بيانات الاختبار للمشروع الحقيقي.
- تحديث README وإضافة هذا التقرير.

لم تُعدّل migrations 001–006 أو Edge Functions المنشورة، ولم يحدث Deploy أو Push أو تعديل لبيانات المشروع الحقيقي.

## توافق SQL

العقد الحالي متوافق مع ملفات migrations المحلية: app_snapshot يعيد currentUser وarrays الخاصة بالنظام. collections تقابل case_payments، وpayroll تقابل employee_salaries، وsalaryPayments تقابل salary_payments، وadvances تقابل employee_advances، وsettlements تقابل advance_settlements، وusers تقابل profiles، وaudit تقابل audit_logs. branches.id هو اسم الفرع النصي نفسه. باقي الحقول تعبر JSONB بالشكل الذي يبنيه RPC.

ملاحظة SQL قائمة لم نغيّرها: app_command في migration 003 يجعل الهاتف فارغًا عند غيابه من caseEdit. عالجنا ذلك عند حدود المستودع ونموذج التعديل، واختبرناه مقابل SQL الأصلي. أي عميل آخر يستدعي RPC مباشرة يجب أن يرسل الهاتف الحالي، وإلا يحتاج الخادم لاحقًا migration مستقلة يوافق عليها المستخدم؛ لا يعاد تشغيل أو تعديل migrations المطبقة.

## نتائج الاختبارات

- `npm run check`: اجتاز فحص صياغة جميع ملفات JavaScript المصدر وخادم التطوير.
- `npm test`: 52 اختبارًا/اختبارًا فرعيًا ناجحًا، صفر فشل. منها 22 اختبارًا للمستودع والمصادقة والجلسات، و5 سيناريوهات داخل اختبار تكامل المستودع مع migrations 001–006 في PGlite معزول (مع احتساب الاختبار الأب أيضًا في الإجمالي).
- `npm run test:supabase-ui`: نجح مسار متصفح موصول بخادم محاكاة؛ رفض دخول خاطئ، قبول جلسة اختبار، قراءة snapshot، حالة وتعديل هاتف ودفعة، إدارة حساب، خطأ انقطاع شبكة دون Demo، تنظيف البيانات عند انتهاء الجلسة، إعادة دخول وخروج.
- `npm run test:case-payments`: نجح سيناريو 30000 ثم 10000 ثم 5000 وتطابق الأرصدة والتحصيلات والتقارير والإلغاء والاستبدال ونموذج الهاتف.
- `npm run test:ui`: نجح مسار الوظائف السابق للموظفين والسلف والرواتب والمصروفات والحسابات والتصدير والتنقل.

اختبارات SQL تعمل على PostgreSQL مضمّن في الذاكرة، مع محاكاة مخطط Auth وأدواره؛ لا تتصل بقاعدة بيانات المشروع. طلبات المتصفح الخارجية معترضة بالكامل. لا تُستخدم بيانات مرضى حقيقية في أي اختبار.

## الفحص الحقيقي المحدود الذي نُفذ

باستخدام URL العام فقط أُرسل OPTIONS إلى login وadmin-users مع Origin: http://localhost:4174. النتيجة لكليهما HTTP 200، وAccess-Control-Allow-Origin مطابق، وPOST وOPTIONS وترويسات apikey/content-type/authorization مسموحة.

أُرسل GET إلى نقطة Auth العامة /auth/v1/settings مع Publishable Key في apikey؛ أعادت HTTP 200. لم يُعرض محتوى الاستجابة أو مفاتيح في السجلات. هذه نقطة إعدادات عامة، وليست بيانات مرضى أو مستخدمين.

هذه الفحوص تؤكد الوصول إلى الخدمات ونجاح الطلب العام بالمفتاح، لكنها لا تثبت تسجيل دخول حساب فعلي أو نجاح RLS وRPC المنشورين أو الحفظ والاسترجاع على مشروع Supabase. لم يُرسل POST لتسجيل الدخول أو RPC حقيقي، ولم تُقرأ أو تُكتب سجلات المركز.

## المطلوب قبل الاختبار النهائي

1. شغّل npm start وافتح http://localhost:4174، ثم سجّل الدخول بنفسك بحساب Auth وprofile نشطين. لا ترسل كلمة مرورك للمحادثة.
2. تحقق من ضبط RATE_LIMIT_SALT في أسرار Edge؛ نجاح OPTIONS لا يختبر الدالة auth_take_slot أو وجود السر. CORS لهذا العنوان نجح بالفعل.
3. تحقق من أن نشر الوظيفتين يتضمن استدعاء p_bucket وp_max_hits المصحح؛ الفحص العام لا يثبت نسخة كود التنفيذ الداخلية.
4. عند اختبار الاستعادة: APP_URL = http://localhost:4174/، وإضافته لقائمة Auth Redirect URLs، مع إعداد البريد SMTP. افتح الرابط على الجهاز الذي يشغّل التطبيق.
5. بعد السماح باختبار فعلي ببيانات اختبار واضحة: أضف حالة ودفعات ومصروفًا وموظفًا، وراجع Audit والأرصدة، ثم افتح حسابًا مصرحًا من جهاز ثانٍ واختبر الاسترجاع والصلاحيات والتعطيل وتكرار الطلبات والتزامن.

القراءة عبر الجهاز الآخر تحدث عند الدخول أو التنقل أو الضغط على تحديث؛ لا توجد Realtime فورية. بعد إعادة تحميل الصفحة يلزم تسجيل الدخول من جديد لأن التوكنات لا تخزن دائمًا، بينما البيانات المرسلة فعلًا لـ Supabase يفترض أن تبقى وتحتاج إثباتًا باختبار القبول الحقيقي.

ملاحظة موارد الاختبار: التشغيل التسلسلي العادي اجتاز المجموعة كاملة أولًا، ثم تعثر اختبار migration في إعادة تشغيل بسبب نفاد ذاكرة V8. اجتاز منفردًا عند تقليل ترجمة WebAssembly؛ أضيف liftoff-only لأمر الاختبارات، دون التأثير على تشغيل التطبيق.
