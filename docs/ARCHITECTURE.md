# هيكل التطبيق وقواعد الحساب

توجد ثلاث طبقات: واجهة `app.js/screens.js/ui.js`، عمليات وقراءة بيانات عبر `repository.js`، وقواعد الحساب في `finance.js` وخدمة الاختبار في `service.js`. لا تعدل النماذج مصفوفات البيانات مباشرة. المستودع المؤقت ينفذ قواعد الخدمة ثم يعيد نسخة من الحالة؛ المستودع المتصل يستدعي Auth/Edge Functions وRPC. SQL هو السلطة النهائية في الوضع المتصل؛ تحقق JavaScript لتحسين تجربة الاستخدام فقط.

## التخزين والعلاقات

- `profiles` مرتبط بـ `auth.users`؛ يحتوي الدور والصلاحيات الصريحة والفروع والحالة النشطة. خزنت الأدوار والصلاحيات داخل profiles بدل تكرارها في جدول user_roles منفصل؛ يمنع RLS والـ grants أي تعديل مباشر من المستخدم.
- `branches`: الفروع الحقيقية، لا بيانات مسبقة في migrations.
- `cases` ← `case_payments`: لكل دفعة حالة محددة، ورقم إيصال فريد حتى بعد الإلغاء.
- `employees` ← `employee_salaries` ← `salary_payments`: استحقاق فريد للموظف والشهر، مع عدد مفتوح من الدفعات الفعلية.
- `employee_advances` و`advance_settlements`: صرف السلف، ثم رد نقدي أو تسوية مرتبطة باستحقاق راتب.
- `expenses`: مصروفات مدفوعة.
- `audit_logs`: قيم قبل/بعد، هوية الخادم والوقت؛ append-only.
- `operation_requests`: مفتاح idempotency لكل مستخدم وطلب ناجح. يعاد الطلب ذاته دون تسجيله مرة ثانية؛ يرفض إعادة استخدام المفتاح ببيانات مختلفة.
- `auth_rate_limits`: محاولات محدودة عبر buckets مجزأة؛ لا تحفظ IP الخام أو كلمة مرور.

معظم جداول المجال لها `id` و`branch` و`data` بصيغة JSONB، مع أعمدة مولدة typed مثل amount وcase_id وemployee_id وsalary_id وnet. العلاقات والقيود والفهارس تقع على الأعمدة typed، والـ RPC يبني payload من حقول مسموحة فقط. اختير هذا للحفاظ على عقد الواجهة الموجود؛ يمكن توسيع الأعمدة الصريحة لاحقًا دون إعادة كتابة الواجهة. معرفات الحالات تسلسلية، وبقية الحركات UUID. التسلسل في PostgreSQL قد يترك فجوة عند فشل معاملة؛ لا يعاد استخدام رقم حالة قديم.

## الحساب

كل المبالغ جنيه مصري حتى منزلتين عشريتين. عمليات جمع JavaScript تجمع بالقروش الصحيحة، وPostgreSQL يستخدم numeric. المستحق = التعاقد − الدفعات الفعالة. إدخال تعاقد لا ينشئ تحصيلًا. يمنع التحصيل الأكبر من الباقي بدلاً من تجاوزه دون اعتماد؛ تدفقات اعتماد التحصيل الزائد غير متاحة حاليًا.

صافي استحقاق راتب = لقطة الأساسي وقت التسجيل + الإضافات − الخصومات الأخرى − السلف المسواة. المدفوع = مجموع salary_payments. المتبقي = صافي الاستحقاق − المدفوع. صرف السلفة يسجل مرة واحدة؛ خصمها يقلل رصيد الموظف وصافي راتبه، ولا ينشئ مصروفًا مستقلًا آخر.

صافي الحركة التشغيلية النقدية = التحصيل − المصروفات المدفوعة − دفعات الرواتب. حركة الخزينة بعد السلف = الصافي − السلف المصروفة + السلف المردودة نقدًا. لا نحسب السلفة المخصومة من الراتب كأموال نقدية دخلت الخزينة. لا يسمى التحصيل ربحًا.

فترة التقرير تشمل طرفي التاريخ حسب يوم الحركة. قيمة التعاقدات تخص الحالات التي دخلت داخل الفترة. العدد وأرصدة الحالات والرواتب والسلف لقطة حالية لكل الفرع، وليست رصيدًا تاريخيًا بنهاية الفترة. توضح الواجهة ذلك. اليوم وتواريخ الإدخال تعتمد التاريخ المحلي لجهاز المستخدم؛ يجب ضبط الأجهزة على توقيت المركز Africa/Cairo عند التشغيل الحالي. التوقيت المسجل في سجل الخادم timestamptz.

الحركات الملغاة تبقى في التقرير مع وسمها ولا تدخل المجاميع. تعديل الدفعة لا يمحوها: إلغاء موثق بسبب ثم حركة بديلة؛ السجل السابق والجديد محفوظان بالتدقيق. لا توجد أزرار حذف مالي نهائي.

## الصلاحيات

الصلاحية تتكون من نشاط وفرع، مع active=true. Super Admin له جميع الفروع والأنشطة؛ الأدوار الأخرى لا تحصل على صلاحيات تلقائية بمجرد تغيير الاسم بل تحتاج grants صريحة. وصول التقارير يمنح قراءة البيانات المالية في الفروع المسموحة. صلاحية الحالات تشمل قراءة دفعات الحالات في فروعها لإظهار الرصيد والسجل بدقة؛ تسجيل/إلغاء دفعة يتطلب finance. لا تمنح صلاحية الحالات قراءة مصروفات المركز أو رواتبه. قبل التشغيل يجب تخصيص دور الموظف وفق ما ينبغي له الاطلاع عليه.

RLS يقيد SELECT، والكتابة المباشرة مرفوضة حتى للحساب الإداري عبر واجهة العميل؛ فقط app_command يتحقق من auth.uid() والصلاحية والفرع ويكتب داخل معاملة، ويأخذ قفلًا لتسلسل فحص الأرصدة والكتابة ومنع سباق دفعتين. وظائف SECURITY DEFINER مضبوطة search_path=''، والـ execute مسحوب من public/anon. snapshot يستخدم SECURITY INVOKER لتبقى RLS نافذة.

إدارة المستخدمين محصورة في Super Admin من Edge Function تتحقق من توكن المستخدم لدى Auth ثم حالته ودوره من قاعدة البيانات. service role موجود فقط ببيئة Edge. إذا فشل تعديل Auth بعد بدء تعديل الحساب يبقى الحساب معطلًا لحين المعالجة، وتظهر رسالة بذلك. لا يعتمد الدور على user_metadata القابل لتعديل المستخدم.

## حدود وضع الاختبار

هوية المدير التجريبي وقواعد الصلاحيات في الذاكرة ليست حدود أمان؛ أدوات المتصفح تستطيع تغييرها. لا بيانات حقيقية أو كلمات مرور محفوظة ولا LocalStorage ولا IndexedDB. تحديث الصفحة يمحو الاختبار. RLS وسجل التدقيق الموثوق لا يعملان على الإنترنت قبل النشر والربط الفعلي.
